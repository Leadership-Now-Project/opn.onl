# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Local machine context, when this checkout sits under `~/work`: read `~/work/AGENTS.md` first.

## What this is

opn.onl — privacy-focused, self-hostable URL shortener. Rust/Axum/SeaORM/PostgreSQL backend (`backend/`), React 19/TypeScript/Vite/Tailwind frontend (`frontend/`). AGPL-3.0.

## Commands

### Backend (`backend/`)

```bash
docker-compose -f docker-compose.dev.yml up -d   # Postgres + Redis for local dev (run from repo root)
cargo run                                        # dev server on :3000 (migrations run automatically on startup)
cargo clippy                                     # lint
cargo build --release

# Tests are real integration tests against Postgres — DATABASE_URL must point
# at a throwaway database (migrations run automatically, once per process):
createdb opn_test
DATABASE_URL=postgres://localhost/opn_test cargo test
DATABASE_URL=postgres://localhost/opn_test cargo test --test integration admin_tests::   # one test file
```

### Frontend (`frontend/`)

Needs Node `^20.19.0 || >=22.12.0` (the `engines` field; `frontend/.nvmrc` is 22): the locked Vite 8 / rolldown declare it, and `npm ci` still installs on older Node before the toolchain fails.

```bash
npm run dev        # Vite dev server on :5173 (honors PORT env var)
npm run build      # tsc -b && vite build (production build also prerenders static pages via Puppeteer)
npm run lint       # ESLint
npm run test       # Vitest unit tests (watch mode; `vitest run` for one-shot)
npx vitest run src/pages/Admin.test.tsx   # single test file
npm run test:e2e:ci   # Playwright, whole Chromium suite (what CI runs on every PR)
```

The Playwright suite runs against the real backend: start it on `:3000` with a **fresh database** and
`TRUST_PROXY_HEADERS=true` first. `frontend/e2e/README.md` has the exact commands.

## Architecture

### Backend

- **`src/lib.rs` is the single source of truth for the app**: `AppState` + `build_router()`. The binary (`src/main.rs`) is a thin wrapper: env, logging, DB connect, migrations, serve. Integration tests import the real router via the lib target (`opn_onl_backend`). `build_router` must stay byte-for-byte what the binary serves; middleware order (with_state → https_redirect → rate limit → CORS → tracing → security headers) must not be reordered.
- **`src/handlers/`** — one module per domain (auth, links, analytics, admin, organizations, folders, tags, passkeys, api_keys, bio, websocket, contact). Handlers do their own auth: they parse the `Authorization: Bearer` header themselves (JWT via `utils::decode_jwt`, or `opn_…` API keys); there is no auth middleware/extractor layer. Admin handlers gate on `require_admin` in `handlers/admin.rs` (checks `is_admin` and excludes soft-deleted users).
- **Link access is org-first** (`handlers/link_access.rs`): a personal link (`org_id` NULL) belongs to its creator; an organization link is decided by the caller's CURRENT membership and role (read: any member, write/clone: editor+, delete: admin+ or the creator while still an editor), and `user_id` gives the creator nothing once they leave. Authorize link handlers with `authorize_link` / `CallerAccess` and scope queries with `readable_links` / `own_links` / `listed_links`; never gate on `link.user_id == caller`. Realtime click events carry `org_id`, and `/ws` / `/sse` route by the subscriber's memberships, refreshed on the periodic token revalidation. The two transports share a per-user connection cap (`WsState::try_acquire`, `WS_MAX_CONNECTIONS_PER_USER`, default 5), `/ws` takes client messages of 4 KiB at most, and every connection ends when the process is told to shut down (`WsState::shutdown_after`, wired into `with_graceful_shutdown` in `main.rs`): an `/sse` stream that never ends would otherwise hold the server open until the orchestrator kills it.
- **`src/entity/`** — SeaORM models. **Soft delete is the norm**: `users` and `links` have `deleted_at`; most list queries must filter `DeletedAt.is_null()`. Soft delete is an UPDATE, so FK `ON DELETE CASCADE` does not fire — related cleanup (e.g. passkeys on user delete) must be done explicitly.
- **Deleted links are purged, and a link id never says whether it exists**: the daily retention task also removes individually soft-deleted links after `ACCOUNT_PURGE_DAYS`, retiring their codes first so they stay reserved. Link-by-id handlers load the link through `link_access::live_link_for`, so a missing, a deleted and a foreign id all answer the same 403 by design; a new one must do the same and not add a 404 for a missing id, which would let callers probe which ids exist.
- **Expiry reminders stamp the link**: a daily task (`utils/link_expiry.rs`, `LINK_EXPIRY_REMINDERS`) mails the owner of each personal link that expires within 3 days and sets `links.expiry_notice_sent_at`, so the link is not listed again. Code that changes a link's `expires_at` must go through `links::set_link_expiry`, which clears the stamp when the date really changes; writing the column directly leaves the new date without a reminder.
- **A destination is stored in a spelling a browser can follow**: the URL parser reads `https:host/x`, `https:/host/x` and `https:\\host\x` as `https://host/x`, but a browser sent that text in `Location` opens a path on the short-link host. `links::validate_url` therefore returns the text to STORE: an address written out (`http://` or `https://`, then the host; `url_policy::is_written_out_http_url`, twin `isWrittenOutHttpUrl` in `frontend/src/utils/destination.ts`) exactly as typed, anything else in the parser's spelling, with every check run on both. Code that keeps a destination (a link's or a routing rule's) must keep that returned value, not the request's text. Rows from before the rule keep their text: nothing rewrites them, `destination_redirect` (every redirect to a destination, cached or not) and the preview answer send them through `url_policy::well_formed_destination`, and the Redis entry holds the stored text. So never compare destinations as text to decide whether one changed: use `url_policy::same_destination`, as `update_link` does, or re-saving such a row would drop its Drive file and media page. `drive::is_drive_url` takes only a written-out address.
- **File links** (`utils/files/`, `handlers/files.rs`, table `link_files`; off unless `FILES_S3_BUCKET` is set, and the `/files` routes then answer 404 to a signed-in caller): a link that serves an uploaded file has the marker `opn-file:<link_files.id>` as its `original_url`. Ask `links::Model::is_file()`, and show `shown_url()` (empty for a file link) wherever a destination is displayed, exported or mailed. The bucket is only reached through the `FileStore` trait (`AppState::files`); tests use `MemoryFileStore` through `common::spawn_real_app_with_files`. Rules that must hold: the address a visitor is sent to is signed inside `GET /{code}` after every check a link has and is never cached, listed or logged (`redirect_is_cacheable`, `cached_redirect_is_servable`); what opens in the browser is decided by `files::served_as` alone; a file link is created only through `links::insert_link` (the same path as `POST /links`) and is never cloned, routed or given a URL; and any code that deletes links, soft or hard, takes `FilesOfLinks` BEFORE the delete and calls `.remove()` after the commit (a hard delete clears `link_files.link_id`). `remove_dead_files` re-checks that a file's link is really gone, so it is safe to over-ask; `Sweep::All` belongs in `integration_serial` tests only.
- **Secure View** (`utils/secure_view.rs`, `handlers/secure_view.rs`, `link_files.secure_view` / `protected_key` / `secure_view_generation`, `secure_view_tickets`, `click_events.viewer_email`; frontend `pages/SecureView.tsx`, `components/viewer/`; inert unless file sharing is on): a file link that opens a viewer instead of handing the file over. `GET /{code}` runs every gate as for any link and then, for such a link, mints a view ticket and answers 302 to `{FRONTEND_URL}/v/{code}#t=<ticket>`; it signs nothing and counts nothing (`files::file_destination` returns `Viewer` before `download_url` can be reached). `POST /{code}/view` (ticket + email) re-runs every gate, uses the ticket up (`spend_ticket`: a ticket opens one view), is where the click is consumed (`consume_capped_click`, once per success) and recorded with `viewer_email`, and returns a view token; `GET /{code}/view/file` streams the bytes through the backend (`FileStore::get`, protected copy first) to a caller with that token in `X-View-Token` or `Authorization`. Rules that must hold: both viewer calls ask the link's checks through the one `still_viewable` (only the click cap differs), so add a check there and nowhere else; a ticket or token is bound to the link, file, password and `secure_view_generation`, which `set_secure_view` raises in the same statement that turns the switch, so switching off ends them for good; an alias that is the word after the code in a `/<code>/<word>` route (`verify`, `preview`, `view`) is reserved, and `frontend/nginx.conf` serves `/r/<code>` and `/v/<code>` before those proxies (`reserved_alias_tests` replays the locations); no answer for a Secure View link contains an address of the bucket; a ticket or token is never accepted from, or put in, a query string (fragment and header only); without a valid ticket or token every refusal is the one `session_expired` 401, also for a missing or deleted code; `viewer_email` leaves the API only through `link_access::can_see_viewer_emails` (creator, organization owner/admin, instance admin) and never in a realtime event or a log, and it is scrubbed wherever a click's IP is (`utils/privacy.rs`); eligibility is `secure_view::eligible`, the same rule as `files::served_as`, with a twin in `frontend/src/utils/secureView.ts`. The protected copy of a PDF is best effort (`protect_pdf`: strict parse, AES-256, empty user password, verified by `fingerprint` over the pages and every stream's stored bytes, else the original is served; it must never inflate a stream, so do not call `get_page_content`, `decompressed_content` or text extraction there, and it works within `ProtectLimits`, which do not bound what lopdf allocates while it reads a crafted file's object streams: the backend container's `mem_limit` in `deploy/lnp/docker-compose.yml` is the backstop) and is made in the background; it is recorded only while the link is live (`make_protected_copy`), `remove_dead_files` deletes it with the original and marks the row only if no copy appeared meanwhile, so nothing is left in the bucket. PDF.js is imported by `components/viewer/pdfDocument.ts` alone (tests mock that file) and runs with `useWasm: false`, which is what lets it work under the stock CSP; `vite.config.ts` copies the decoders, CMaps and standard fonts it fetches on demand to `dist/pdfjs/`. `VITE_PUBLIC_LINKS_ONLY=true` (the LNP public image) reduces the header to the logo.
- **Google Drive links** (`utils/drive.rs`, table `link_drive_files`, frontend `src/utils/googleDrive.ts` and `DriveFilePanel.tsx`; off unless `GOOGLE_PICKER_API_KEY` and `GOOGLE_PICKER_APP_ID` are set with Google sign-in, read once into `AppState::drive`): an ordinary URL link to a file's address in Drive, plus a row saying which Drive file it is. The server never receives a Google token: the token, the picker and every Drive call are in the browser, the token only in memory and only for the `drive.file` scope. Rules that must hold: the one request that changes anything in Drive is `shareWithAnyone`, sent only after the person ticked the box and clicked Create, and before `POST /links`; a refused change creates no link; sharing Google would not list is `unknown`, never assumed. A file's sharing is never changed for a link our own server would then refuse: the limits in `DriveFileRef::checked` / `is_drive_url` have a twin in `googleDrive.ts` (`DRIVE_LINK_LIMITS`, `driveLinkProblem`, `cleanDriveName`, `isDriveLinkUrl`) that runs when the file is picked, the alias is checked just before the change, and the two sides change together. If the link still fails after the change, the message says the sharing was changed and no link was made (`linkFailure`), and a retry sends no second change. Every way out of a session calls `forgetDriveToken` from `utils/driveToken.ts`, the one Drive file the entry bundle may import. `POST /links` stores a `drive_file` only with an `https` destination on `docs.google.com` or `drive.google.com` (`drive::is_drive_url`); a row exists only for such a link, which is how the lists (`attach_file_info`) and the deletes (`drive::forget_for_links`) run no query for any other link, and a changed `original_url` removes the row in the same transaction. Stock images allow none of Google's picker hosts: `CSP_GOOGLE_DRIVE_PICKER` is set for the LNP dashboard image only.
- **Media links** (`utils/media.rs`, `handlers/media.rs`, table `link_media`; frontend `pages/MediaPage.tsx`, `CreateMediaTab.tsx`, `src/utils/media.ts`): an ordinary URL link to a video's own page (YouTube, Vimeo, a video in Drive) plus a row saying which video, that opens a page with the player on it. `GET /{code}` runs every gate as for any link, consumes and counts the click, then answers 302 to `{FRONTEND_URL}/m/{code}#t=<ticket>`; `POST /{code}/media` trades the ticket for the title, the player's address and the button, counts nothing, and may be repeated for the ticket's hour (the page keeps the ticket in the address so a reload works). Rules that must hold: the server alone decides which video a link is for (`parse_media_url`; its twin `parseMediaUrl` in `src/utils/media.ts` only draws the hint, and the two change together) and stores its own spelling of the address (`canonical_url`), never the request's; the player's address is built by `embed_src` from the stored provider and an id it checks again, so it is only ever on one of `EMBED_ORIGINS`, the same three origins as `MEDIA_EMBED_ORIGINS` (the page's own check) and `CSP_MEDIA_EMBEDS` (the LNP public image's `frame-src`; a policy has one `frame-src`, so with `CSP_GOOGLE_SIGN_IN` the players join that directive); no request field carries a player address; a row exists only for a link whose destination `could_be_media`, which is how every other link's redirect, list and edit run no query, and why such a destination is never written to or served from the Redis redirect cache (`redirect_is_cacheable`, `cached_redirect_is_servable`): a cached destination would skip the page; the ticket is bound to the link, its code and its password, so a password-protected link gives no video without the password, and without a valid ticket every refusal is the one `session_expired` 401, also for a missing, deleted or non-media link; the button's link is `https` only and passes `validate_url` (`checked_media_cta`), and is checked again on the way out; the embed check (`EmbedChecker` on `AppState::embed_check`, `MEDIA_EMBED_CHECK`, tests inject a stand-in through `common::spawn_real_app_with_embed_check`) fetches only the two fixed oEmbed addresses, follows no redirect, and refuses a link only on the host's own "no" (`verdict_from`), never on our own failure to reach it; a Drive media link is a Drive link whose `drive_file` is a video, made through `DriveFilePanel`'s `media` mode, so the sharing rules above apply unchanged, and the button is checked (`ctaProblem`) before the sharing can be changed; a changed `original_url` removes the row in the same transaction, a clone copies it, and a media link has no routing rules. `m` and `media` are reserved aliases; `frontend/nginx.conf` serves `/m/<code>` with `/r/` and `/v/`, before the `/<code>/media` proxy.
- **`migration/`** — SeaORM migration crate; migrations run automatically on startup and on first test-suite connect.
- **`utils/`** — `ClickBuffer` (batches click events before DB flush), `RedisCache` (optional redirect cache — handlers that change link state must invalidate it or blocks/edits take up to the TTL to apply; use `links::invalidate_cached_codes` / `active_link_codes_for_user`), `EmailService` (optional; unset SMTP = verification/reset/password-changed emails are skipped and `POST /contact` answers 503, since the message has nowhere to go; every email is an `EmailBody` with a text part and an HTML part; mail that a request can trigger goes through `EmailService::reserve` first — per-recipient cooldown, per-client budget and the split hourly pools live in `utils/email_limits.rs` — and a handler that gets `Err` must send nothing **and must not rotate the stored token**, because the link already mailed would die; `ClientKey` in the request extensions is the client the rate limiter charged), `BackupService` (S3; optional; when configured, `spawn_backup_task` in `main.rs` backs up every `BACKUP_INTERVAL_HOURS` (default 24, 0 = off, first run one interval after boot) and prunes to the newest `BACKUP_KEEP` automatic backups (default 14, minimum 1). Scheduled backups are named `backup_auto_YYYYMMDD_HHMMSS.sql.gz`, manual ones `backup_YYYYMMDD_HHMMSS.sql.gz`: the schedule's prune never touches a manual backup, only `DELETE /admin/backup/cleanup/{keep}` does (both kinds, keep >= 1), and nothing outside these two name patterns is ever listed or deleted), rate limiters, JWT, GeoIP, privacy sweep (IP truncation at collection, retention anonymization; referer stored host-only; `purge_click_pii_for_user` on account delete). Optional settings and on/off switches are read through `utils::env` (`env_nonempty`, `env_flag`, `env_parse`): compose passes an option left alone as an empty string, so blank must mean unset, and every switch accepts true/false/1/0/yes/no/on/off in any case. Do not parse a boolean with `== "true"` or `parse::<bool>()`. `RateLimiters` lives on `AppState` (shared by the rate-limit middleware and handlers, e.g. the redirect password path enforces the `password_verify` limiter in-handler). Middleware classifies redirect vs API by route prefix, not path length.
- **Timestamps leave the API as RFC 3339 UTC** (`2026-11-15T04:59:00Z`). Every `*_at` column is a naive `TIMESTAMP` holding UTC; format it with `utils::time::utc_rfc3339`, never `NaiveDateTime::to_string()`. Browsers read an offset-less time as local time, which shifted every displayed time by the viewer's UTC offset until 2026-09.
- **Errors are JSON `{"error": "..."}`**: build them with `handlers::json_error` (or the file's existing `ErrorResponse` / `serde_json::json!` pattern), never a bare `(StatusCode, "text")`, which sends `text/plain` and makes clients guess per endpoint. The one exception is `GET /{code}`: a missing or dead link goes through `links::dead_link`, which answers a browser with a small HTML page and anything else with the plain reason. Validation messages from `validator` go through `utils::validation::validation_error_message`, whose output never includes the submitted value.
- **bcrypt only through `utils::jwt::{hash_password, verify_password}`**: both are async and run on the blocking pool. Calling `bcrypt::hash`/`verify` inline in a handler stalls the Tokio worker and every redirect scheduled on it. New account and link passwords are capped at `MAX_PASSWORD_BYTES` (72, bcrypt's input limit); login and link unlock accept any length so older passwords keep working.
- **Rate limits**: only `POST /auth/*` spends the 10-per-minute sign-in budget; `GET /auth/me`, `/auth/settings` and the other reads are on the general bucket (every page load makes them). 429s carry `Retry-After` (rounded up) and `X-RateLimit-*`. `build_cors()` echoes the requested headers (`Access-Control-Allow-Headers: *` does not cover `Authorization` under the Fetch spec) and exposes the rate-limit headers, because production is split-origin.
- **Email addresses are lowercase**: `normalize_email` stores and compares the whole address in lowercase, with a Unicode domain as punycode. Look users up with `email_domain_policy::live_users_by_email` (compares `lower(email)` over live rows; on a legacy case collision it prefers the exact spelling typed, then the oldest account), never `Column::Email.eq`. The `fold_user_email_case` migration folded existing live rows and left collisions alone: they are counted in the startup log and `email_case_collisions` on `/admin/stats`, and the `lower(email)` unique index exists only where there were none.
- **Auth/roles**: single `is_admin` flag on users (no role table). First registered user becomes admin (`ensure_admin_exists`). `token_version` on users invalidates old JWTs on credential change. `JWT_SECRET` is validated at boot (rejects short / known-placeholder values).
- **Route order matters**: `/:code` redirect routes are registered last so they don't shadow API routes.
- API docs generated via utoipa; new handlers should carry `#[utoipa::path]` annotations and be registered in `src/openapi.rs`. The served document is built by `openapi::api_doc()`, which stamps `CARGO_PKG_VERSION` — **do not put a `version` literal back into `#[openapi(info(...))]`** (utoipa only accepts a literal there, which is exactly how the published spec ended up advertising 1.2.1 after 1.3.0 shipped).

### Frontend

- SPA with react-router (`src/App.tsx`). Marketing pages are **eagerly imported** so the production build prerenders them to static HTML (SEO); app pages (Dashboard, Admin, Settings…) are lazy-loaded and not prerendered.
- **Adding a page route requires touching up to four places**: `src/App.tsx` (route), `vite.config.ts` `PRERENDER_ROUTES` plus its `SITEMAP_HINTS` entry in `src/utils/sitemap.ts` (only if it should be prerendered — a route without hints, or hints without a route, fails the build), and `frontend/nginx.conf` SPA-route allowlist regex (production only — anything not on that allowlist matching `/[a-zA-Z0-9_-]{1,255}` is proxied to the backend as a short-link code and will 404 as a page; that range is every length the backend can store, since `MIN_ALIAS_LENGTH` / `MAX_ALIAS_LENGTH` are unclamped env vars. The SPA's short `/404` route is on the allowlist for that reason).
- **`sitemap.xml` and the `Sitemap:` line of `robots.txt` are generated at build time** (the `generate-sitemap` plugin in `vite.config.ts`, builders in `src/utils/sitemap.ts`) from `VITE_FRONTEND_URL` (default `https://opn.onl`) and `PRERENDER_ROUTES`. Do not put either back under `public/` with a domain in it: a hard-coded sitemap once made every build for another domain fail `scripts/verify-prerender.mjs` and made 15 `SEO.test.tsx` tests fail after `cp .env.example .env`. `SEO.tsx` takes its canonical base from the same `normalizeSiteUrl`, `verify-prerender.mjs` checks each page's canonical and the robots.txt line against the generated `dist/`, and `SEO.test.tsx` runs the same generator, so all of them agree for any `VITE_FRONTEND_URL`.
- API access goes through `src/config/api.ts` (`API_ENDPOINTS`, `authFetch` — reads JWT from localStorage). No state-management library; pages fetch directly.
- **Never touch `localStorage`/`sessionStorage` directly**; use `src/utils/storage.ts`. When a visitor blocks site data, storage access throws, and one unguarded read during render used to replace every page, the public ones included, with the error screen.
- Show short links with `shortLinkBase()` / `shortLinkHost()` from `src/config/api.ts`, never a literal `opn.onl` (self-hosted instances have their own host). Count labels go through `src/utils/plural.ts`.
- Prerender in Docker must use Playwright/Puppeteer's bundled Chromium — Debian's apt chromium SIGTRAPs in the builder container (see vite.config.ts sandbox flags).
- **Runtime config is injected at container start, never at build time** (one image serves every deployment): `docker-entrypoint.sh` substitutes `%%GA_ID%%` / `%%GA_CONSENT_MODE%%` in **every `*.html` under the web root**, not just `index.html` — each prerendered route ships its own copy of the placeholders, so substituting only the SPA shell leaves the config dead on 11 of 12 pages. `scripts/test-entrypoint.sh` pins this and runs in CI. Anything that reads these values (`ConsentBanner`, the analytics disclosure on `Privacy.tsx`) must treat an unsubstituted `%%…%%` placeholder as "unknown", because that is what the prerenderer and `npm run dev` see.

### Deployment

- Production: docker-compose + Cloudflare Tunnel; frontend nginx proxies `/{code}` redirects and `/{code}/verify|preview` to the backend, serves prerendered HTML for static routes, and falls back to the SPA shell.
- **HTML is served `Cache-Control: no-cache`; only content-hashed assets are cached (1 year, immutable).** HTML carries both the hashed asset names and the entrypoint-injected runtime config, so a cached shell pins a returning visitor to the previous deploy — that is why the old consent banner survived the 1.3.0 rollout. The header comes from a `map` on content type, deliberately not from per-location `add_header` (which would drop every inherited security header). The CI header smoke test asserts it.
- **nginx logs no visitor data.** The image's stock http-level `access_log ... main` writes the client address, `X-Forwarded-For`, referrer, user agent and the full request line (including the `?token=` of reset/verify links) to stdout, and `frontend/nginx.conf` only replaces `conf.d/default.conf`. The server block therefore sets its own `access_log` with the `privacy` format (time, method, path without query, status, bytes, duration). Never add `$remote_addr`, `$http_x_forwarded_for`, `$http_referer`, `$http_user_agent`, `$request` or `$request_uri` to a `log_format`; the CI header smoke job checks the format and replays a token request against a running container. `error_log` is untouched.
- **Referrer-Policy on redirects comes from the backend alone.** nginx adds its `strict-origin-when-cross-origin` default only when the upstream sent no policy (the `$default_referrer_policy` map; an empty value adds no header), so a proxied redirect carries the backend's `no-referrer` exactly once. `proxy_hide_header Referrer-Policy` would not do: it would remove the backend's value and leave nginx's.
- Images are built by GitHub Actions on push to the `release` branch (`ghcr.io/ysalitrynskyi/opn-{backend,frontend}` multi-arch amd64+arm64); Portainer compose files consume `:latest` or a pinned version tag.

## Releasing

Backend and frontend share one version number. Bumping it means editing exactly these places — everything else derives:

| Place | Note |
|-------|------|
| `backend/Cargo.toml` (`version`) | Source of truth for the backend. |
| `backend/Cargo.lock` | Run `cargo update -p opn_onl_backend --offline` (or any cargo command) so the lock records the new version. |
| `frontend/package.json` (`version`) | Read at build time only, for the structured data's `softwareVersion` in `SEO.tsx`. Keep it in lockstep so an image tag means one thing. |
| `README.md` | The "pin a release tag such as `:X.Y.Z`" example, so copy-pasters don't pin a stale tag. |

Deliberately **not** a place to edit: the OpenAPI `info.version` (reads `CARGO_PKG_VERSION`, see the Backend notes), image tags and release-notes versions (CI derives both from the git tag).

**What PR CI does not see.** The backend toolchain is pinned to 1.98.1 in
`backend/rust-toolchain.toml`, in every CI job that installs Rust, and in the release image
(`rust:1.98.1-alpine3.21`, same Alpine release as the runtime stage). PR CI builds
`backend/Dockerfile` for linux/amd64 only, does not push it, and skips that build when the diff
does not touch `backend/` or `.github/workflows/`. It does not build linux/arm64, so a musl
failure that exists only on that architecture still waits for the release workflow. The frontend
job runs `npm run build` (typecheck, Vite, prerender, and `verify-prerender: OK`). It does not
build the frontend image; the headers job builds only the nginx config stage. Migrations run at
backend start, before it serves anything, so a migration that rewrites a large table (a column
type change on `click_events`, say) is downtime. Check the table size and say so in the release
notes.

Release flow, in order:

1. Feature branch → PR → all CI checks green → merge to `main`. **Branch from `main`** — cutting a branch while still checked out on `release` drags release-only history into the next PR (that is how the deploy host's postgres port leaked into `main` before 1.3.1).
2. `git checkout release && git merge main -m "chore(release): sync main for vX.Y.Z"`. `release` carries no deliberate deviation from `main` any more — host-specific settings are env vars (e.g. `POSTGRES_HOST_PORT`), so `git diff main release` should come back empty. A conflict here means someone re-introduced a branch-local difference; fix that rather than resolving it every release.
3. Push `release` — this builds and publishes multi-arch `:latest`, but only after CI has passed on that commit: the workflow's first job (`CI passed on this commit`, `.github/scripts/wait-for-ci.sh`) waits for a push-started CI run on the same SHA and fails if none succeeds, so the images appear about one CI run later than the push. The tag and release runs gate the same way (CI ran on the commit through `main` / `release`). After a red CI is fixed by a re-run, re-run the image workflow too. `docker-build.yml` keeps one concurrency group per ref, so the tag and release runs can no longer cancel the `release` run that publishes `:latest` (they did on 1.4.0, when the group was repo-wide). Two pushes to `release` in quick succession still collapse into one run for the newer commit.
4. Tag `vX.Y.Z` on the release merge commit, push the tag, then `gh release create` (notes follow the shape of the previous releases: Summary / themed sections / Images / Upgrade).
5. Both the tag push and the release publication trigger `docker-build.yml` for the same tag ref, so they share a concurrency group and **the earlier queued run reports `cancelled`** — expected, not a failure. The surviving run publishes the `X.Y.Z` tags.
6. Verify before declaring done: `docker manifest inspect ghcr.io/ysalitrynskyi/opn-backend:X.Y.Z` (and `opn-frontend`) must list both `linux/amd64` and `linux/arm64`, and the same for `:latest`. Check that `:latest` is really the new build, not only multi-arch: `docker buildx imagetools inspect ghcr.io/ysalitrynskyi/opn-backend:latest --format '{{ with (index .Image "linux/arm64") }}{{ index .Config.Labels "org.opencontainers.image.revision" }}{{ end }}'` must print the release commit.

Deployment to production is a manual Portainer redeploy by the operator; a green release workflow only means the images exist.

## Testing conventions

- Backend integration tests use `common::spawn_real_app()` (real router + real Postgres via `axum_test::TestServer`). Write new tests this way — do not stub the router or hit a running server with shell scripts.
- **Where a test file goes.** Every top-level file in `backend/tests/` is a test binary that links the whole app, and one per file made a debug build 20–30 GB (2026-10). So:
  - New files go in `backend/tests/integration/`, one test binary: add a `mod` line to its `main.rs`. Its tests run in parallel on one fixed environment (`common::baseline_env`), so they may not change an environment variable or sweep the whole database.
  - A test that changes an environment variable (link caps, public URLs, retention windows, switches turned off) or sweeps the whole database (purges, retention scrubs) goes in `backend/tests/integration_serial/` and starts with `let _serial = common::serial_guard().await;`, which runs it alone and puts the environment back afterwards.
  - The files left at the top of `tests/` need a process of their own, and their headers say why: a counting global allocator, log capture that depends on `tracing`'s per-process callsite cache, and proxy-header trust, which the app reads once per process. Add a new one only for the same kind of reason.
- For WebSocket/SSE tests use `common::spawn_real_app_ws()`, which builds the router over an HTTP transport (mock transport can't upgrade) with a real `WsState` so you can broadcast and observe what a `/ws` subscriber receives (see `tests/integration/websocket_comprehensive_tests.rs`). Requires the `axum-test` `ws` feature.
- Tests run in parallel against one shared database: generate unique emails/codes via `common::unique_email()` / `unique_code()`, and don't assert on global counts.
- Frontend unit tests colocate as `*.test.tsx` next to the component (Vitest + Testing Library, jsdom).
- Playwright specs in `frontend/e2e/` run against the real stack. Use `e2e/support/api.ts`:
  `createUser` (registers through the API and verifies through the admin endpoint; there is no SMTP),
  `signIn(page, user)`, `createLink`, and `page.setExtraHTTPHeaders(clientIpHeader())` so a spec never
  spends the per-address rate-limit budget another spec asserts on. Mock with `page.route` only what
  cannot be produced for real (a 500, a network failure, GeoIP data), with a comment saying why. Never
  write `if (await el.isVisible()) { … }`: it passes when the element never renders, and dozens of
  the old specs could not fail because of it.
- Mutation-check new regression tests: break the production code, watch the test fail, restore.
